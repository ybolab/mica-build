# Board dossier: s905x5m

## Identity

X88 Pro X5M / BM201, Amlogic S905X5M (S7D), `MOS_ARCH=arm64`.
The board implementation is in `boards/s905x5m/`.

## Boot chain

The paired MOS Amlogic firmware runs from eMMC boot0 and selects the current
SD system disk (`mmc 0`). The one-second native console countdown consumes no
trial. Automatic boot arms the 60-second Meson watchdog, selects a bounded native
record, persists and reads back the attempt, then verifies the selected FIT with
the required public key embedded in the final exported BL33 control DTB.

The signed kernel supplies its forced command line, content certificate and
native init. The vendor watchdog is set to userspace feed mode with a 60-second
DT timeout; the driver applies NOWAYOUT before device registration. Native init authenticates deployment metadata and mounts verified
root/support components. There is no cfgload, imported environment, raw-slot
installer or old-state migration in this path. Development console access and
opaque vendor stages mean this is not a hardware-rooted assurance claim.

## Storage media and layout

The SD GPT contains FIRMWARE from sector 64 to 128 MiB, SYSTEM from 128 to
1152 MiB, and DATA from 1152 MiB with a 256 MiB factory seed. Only DATA grows.
The two 64 KiB boot records are at absolute 120 and 124 MiB. FIRMWARE contains
records and zero padding; it does not contain an SD bootloader.

The signed external firmware receipt describes the eMMC boot0 payload after its
512-byte vendor-generated header, bounded to 4,193,792 bytes. Native readback
finds the eMMC hardware boot partition independently of the SD system disk.
The firmware and signed receipt remain beside the SD image for offline checks.
Ordinary root/kernel updates do not write firmware. Complete eMMC OS installation
is outside this SD-first milestone.

## Console

The serial console is `ttyS0` at 921600 baud, with
`earlycon=aml_uart,0xfe07a000`. Confirm the connector and voltage against the
specific board's hardware record before wiring. HDMI output depends on the
vendor display initialization and the board kernel/DT.

## Peripherals

The board declares Wi-Fi and Bluetooth using the Seekwave SWT6621/EA6521QF
firmware and SDIO transport. Bluetooth uses the vHCI bridge, not a UART
attach helper. Its derived address persists in protected `DATA/state/bluetooth`, mounted at
`/var/lib/bluetooth` by the shared Bluetooth package; `bdaddr` is stored there; BlueZ uses the hostname plugin for the name.

`BOARD_HWINIT_CONFS` maps audio to ALSA routing, wireless to rail/module
initialization, and Bluetooth to the bridge. The radio packages are selected
independently: declining Wi-Fi retains the shared SDIO transport if Bluetooth
still needs it. Ethernet, HDMI and USB support remain in the kernel/DT and
vendor initialization. No status LED or board recovery action is declared.
RTC retention and the full peripheral matrix need qualification on this image.

The BM201 front panel is an optional local package selected with
`MOS_ROOTFS_COMPONENTS=bm201-front-panel`. Its executable service reads
`/run/mos/timezone` on each update. Declining both radios omits the shared rail
initializer; selecting Bluetooth alone does not load the Wi-Fi driver.

## Recovery method

`make s905x5m-uboot-package` packages the new MOS firmware with the pinned
Amlogic recovery inputs and verifies pack/unpack readback. Install/recover the
paired firmware through the board's Amlogic procedure; generic MOS firmware
maintenance deliberately refuses this hardware-boot target. No automatic flash
or OS physical-recovery action is advertised. The native console remains
available before boot selection. Actual installation and recovery need bench
qualification; building a recovery package does not establish those results.

## Known limitations

The development image producer is implemented, but `BOARD_RELEASE_TARGET=0`
remains until current physical qualification is recorded. SD boot requires the
paired MOS firmware in eMMC boot0; original vendor firmware does not implement
this signed-file policy. No compatibility reader, historical-layout installer
or existing-state migration is provided. Opaque Amlogic stages and radio firmware
retain their recorded auditability and distribution-license limits.

Historical mainline-image and hardware observations remain in RFCT-942 through
RFCT-945. They do not qualify a current component image and are not reused as
current pass results.

## Assurance level

Required FIT/content/metadata verification is implemented and checked offline.
No current hardware boot-assurance level is claimed. Physical cold boot,
watchdog handoff, installation, recovery and hardware-rooted policy remain
unqualified.
