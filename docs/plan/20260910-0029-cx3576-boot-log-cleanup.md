### Exact initramfs memory accounting

The current `_out/cx3576/components/kernel/initramfs.cpio` matches the log:

- Archive: 33,615,360 bytes, SHA-256
  `a140dd702de5c4905a34d320ee406f720327e2ae29c619353d5afa309e4461cb`.
- The kernel logs `Freeing initrd memory: 32824K` at 5.986299 seconds. This
  releases the original archive buffer, not all extracted files at that instant.
- Extracted startup files are consumed by `/init`; the existing util-linux
  `switch_root` removes files from the old initramfs when switching to the
  verified root. Open references can delay individual page reclamation.
- MOS deliberately copies the `/exitrd` closure to a separate tmpfs at
  `/run/initramfs` before moving `/run` into the real root. It contains the
  shutdown executable and libraries needed after the file-backed root is detached.
- Archive inventory: 20 regular exitrd files contain 17,253,688 bytes
  (about 16.45 MiB; 17,293,312 bytes when rounded per file to 4 KiB pages).
  This is an artifact measurement, not a live-board RSS measurement. File-system
  metadata and additional runtime files affect actual usage.
- The tmpfs `size=36M` is a limit, not a 36 MiB allocation. The retained shutdown
  environment explains ongoing memory use; the full 32.1 MiB archive is not a
  permanent reserved RAM disk. Compression alone would not reduce the unpacked
  shutdown closure's steady-state footprint.

Primary implementation references: `pkgs/mos-boot/initramfs.sh`,
`pkgs/mos-deploy/src/bin/mos-init.rs` (copy, tmpfs mount, and switch_root),
[the pinned kernel initramfs implementation](https://github.com/armbian/linux-rockchip/blob/c6157104418d012823413c02f9222f3fe123dd25/init/initramfs.c),
and [util-linux switch_root](https://github.com/util-linux/util-linux/blob/v2.41/sys-utils/switch_root.c).

## Proposal

### 1. Bind evidence and establish focused regressions

Record the source revision, dirty state, component IDs, image checksum, resolved
kernel config, and decompiled DTB for the candidate. Compare against the complete
historical log without treating old geometry as the acceptance baseline. Resolve
all paths and enabled nodes from the compiled DTB, including inherited DTS files.

Extend existing BSP/build/boot tests where behavior changes. Establish RED for
orphan camera topology and required config/resource mismatches before fixing
them. Use actual pinned source or compiled artifacts instead of tests that merely
search for a new line of source. FIT descriptions need artifact inspection, not
a dedicated test framework or a behavioral TDD ceremony.

Verification: the initial reproductions fail for the named defects; already
working signed boot, watchdog, MAC, and repart tests remain unchanged baselines.

### 2. Correct the board device tree and kernel configuration

In `boards/cx3576/bsp/kernel/dts/rk3576-cx3576z.dts`, remove the unused EVB camera
include together with the now-invalid IMX415 path override. Disable any remaining
orphan CSI/CIF/ISP route introduced by inherited files, using the merged tree to
check endpoints. Keep shared acceleration resources needed outside that route.
This preserves the currently disabled camera product behavior.

Disable the Linux OP-TEE node and unused OP-TEE transport/RNG options after
confirming that active SCMI clocks, reset, and power handling use other paths.
Keep required SCMI services. BL31 is the pinned vendor
`rk3576_bl31_v1.24.elf`, not built from source here. Linux changes cannot remove
its `No OPTEE` and `opteed_fast` messages. Record these as a firmware limitation
unless a supported no-OP-TEE build is available and separately qualified; do not
add BL32 or alter a vendor binary solely to remove text from the log.

Remove zero-length firmware-logo/LUT reservations and their consumers only where
MOS does not use that handoff. Preserve Linux framebuffer/logo support and HDMI
hotplug. Set GPU interrupt names consistently with the Bifrost driver. Disable
MALI400. Enable AUTOFS_FS in the board delta and add an assertion on the resolved
config. Prefer the board configuration layer over broad changes to all boards.

Verification: DT compilation and semantic inspection, resolved-config checks,
GPU probe, no orphan camera probes or Linux OP-TEE UID failure, no zero-size
reservation warnings, and no missing autofs4. Boot with HDMI disconnected; later
check logo/display/hotplug with a display connected when equipment is available.

### 3. Resolve accelerator and remaining resource diagnostics

For VENC/VDEC, use the existing fixed clock configuration as the baseline. If the
merged tree intentionally has no OPP table, make the RK3576 path explicitly skip
DVFS setup rather than reporting an initialization failure. If a required OPP
configuration was actually lost, restore it only from matching board/SoC source
with validated supplies. Do not guess voltages, raise clock limits, disable
system-wide devfreq, or assume that a completed probe proves encoding works.

Check the missing decoder reset names against the RK3576 reset implementation.
Treat only truly optional resources as optional, retaining the resets needed for
error recovery. Record and compare the applied clock rates under real workloads.

For NPU MMIO, identify the reservation owner using the merged DT, pinned driver,
and `/proc/iomem` on the board. Remove a duplicate declaration if proven; if the
mapping is legitimately shared, use the corresponding documented access model.
Do not bypass exclusive ownership more broadly or simply hide the error. Run a
known small inference with checked output and repeated execution.

For the remaining resource rows in the classification table, identify the source
call site and consumer. Remove unused board declarations; fix required clock,
IRQ, regulator, cache, or reset descriptions only from hardware evidence. Keep
optional-resource behavior explicit. Missing documentation or unavailable
firmware remains an identified open item with its functional impact, not a pass.

Verification: representative encode/decode and inference, GPU operation, reset
recovery where the harness supports it, and a reviewed log delta. Check CPU/GPU
thermal control after any supply or OPP change. Routine UART/USB/network operation
must remain functional. No blanket log-level reduction is an acceptable fix.

### 5. Verify initramfs release and retained shutdown memory

Use read-only CPIO inventory and the board collector to record original archive

The command examples belong in the existing bench collector/documentation; do

Verify that `/init` has handed off to systemd and that cleanup leaves no old-root

Keep the shutdown closure because it releases verity/loop/SYSTEM/DATA resources
without depending on the root being torn down. Optimize duplicate libraries or
compression only if a separately measured goal calls for it; neither is required

verify the existing exitrd cleanup behavior after any closure-related change.

Verification: archive-buffer release, expected handoff, explained retained tmpfs
usage, no accumulating memory/file growth across boot cycles, and successful
shutdown cleanup. Emulator evidence supplements but does not replace board data.

Verify first-boot DATA growth, primary and backup GPT consistency, fixed 1 GiB

Reuse the original watchdog task's procedures for U-Boot/Linux/systemd handoff,

Verification: collect explicit pass/fail/not-tested for every required service

## Risks

- Camera includes and logo regions have phandle consumers; removing only the
  provider can break compilation or unrelated display/media paths.
- OP-TEE/SCMI options can share consumers. Preserve needed services, and make the
  vendor BL31 limitation explicit rather than claiming it is fixed by a DT change.
- Clock, voltage, reset, and NPU ownership changes require hardware evidence and
  workload validation. Probe success alone is insufficient.
- Removing the retained exitrd can break shutdown of the file-backed root.
  Its measured memory cost is intentional under the current design.
- Every signed-artifact change must flow through packaging and signing, even if
  only Description metadata changes.
- Historical log observations cannot validate the new layout or rebuilt payloads.
  Board-only acceptance may remain pending until the required device/peer exists.
