## Context

Baseline: `d64b23a7` plus the current uncommitted writable-var/regdb changes.
The requested board is `boards/s905x5m/` (BM201 / X88 Pro X5M). This is full-tier
work spanning board firmware, component packaging, native deployment and checks.

1. `board.env` declares BSP facts and `BOARD_RELEASE_TARGET=0`, with no current
   MOS layout. `rootfs/packages/board-s905x5m.pkgs` and the board's Debian
   producers are absent. Its README still advertises retired image, RAUC and
   eMMC installer commands. `make -n os-image-s905x5m-sd` returns:
   `make: *** No rule to make target 'os-image-s905x5m-sd'.  Stop.`
2. The U-Boot config still selects `run boot_default`; the local menu invokes
   cfgload and the old installer/script path. Its export gate permits missing
   FIT signatures with a warning. The native bounded MOS boot record and
   required-signature path implemented for CX3576 are not integrated here.
3. The common kernel fragment requests `certs/mos-verity-anchor.pem`, but the
   S905X5M Makefile/Dockerfile do not supply a trust context or stage that file.
   Its board config leaves NOWAYOUT disabled and the vendor watchdog modular;
   it lacks the forced current command policy and regulatory certificate export.
4. `build/src/kernel-package.ts`, `pkgs/mos-boot/fit.sh` and the firmware/image
   producer assume CX3576's FIT addresses, DTB, DesignWare watchdog, Rockchip
   magic and loader ranges. `file-layout.ts` fixes its 16/17 MiB environments
   and 18 MiB SYSTEM start. `mos-deploy` recognizes S905X5M component identity,
   but rejects its boot backend and firmware, and fixes FIT environment offsets.
5. The retained Seekwave vHCI bridge, radio rail initialization, audio setup,
   front-panel implementation and blobs are inputs for the new packages.
   The bridge expects `var-lib-bluetooth.mount`, which the removed board
   producer no longer supplies. The current shared var policy provides bounded
   DATA/var plus protected DATA/state; Bluetooth credentials must use the latter.
6. Historical board evidence in PLAN-910 establishes that GPT SD boots used the
   U-Boot installed in eMMC, not a loader inside the SD image. eMMC boot0/boot1
   use a target-generated 512-byte header and are not raw SD-loader destinations.
   Vendor writes occupy 36–100 MiB and 108–116 MiB of the eMMC user area. These
   hardware constraints need verification against the pinned source before
   freezing the new layout; they are not old-OS compatibility requirements.
7. The baseline package resolver currently fails before board selection because
   producer discovery scans existing `.tmp` source snapshots as duplicate
   `board-cx3576` producers. This also affects the concurrent storage work.
   Verify this port in an isolated source snapshot without those staging trees;
   do not remove other work or broaden this task into producer-discovery cleanup.

## Proposal

### 1. Freeze the board boot and storage contract

Use the current signed-file architecture, retaining two deployment records,
SYSTEM component files and a quota-enabled DATA partition. Keep public trust
material separate from private signing inputs and retain the native development
U-Boot countdown and console.

The working delivery order is SD development first, with the corresponding new
MOS U-Boot artifact required in the eMMC boot area. The SD image must not claim
standalone boot through the original cfgload firmware. A fresh eMMC complete
system/installer package is a subsequent milestone unless selected for this task.
No device write is part of this proposal.

Start from a three-partition FIRMWARE/SYSTEM/DATA candidate. A protected first
region ending at 128 MiB can contain the documented vendor reservations and
separate 64 KiB native records at 120/124 MiB; SYSTEM can start at 128 MiB with
1024 MiB capacity and DATA at 1152 MiB with a 256 MiB factory seed. These are
proposal values, not qualified offsets. Verify source writes, GPT handling,
record durability and payload capacity before adopting them. The bootloader
remains a separate Amlogic hardware-boot artifact, not a Rockchip raw blob placed
in the first GPT partition. No historical environment or state is imported.

Verification: layout overlap/refusal fixtures, exact partition/GUID checks,
protected-range sentinels, boot0/boot1 framing and Amlogic package round-trip.

### 2. Implement required signed native boot

Integrate the existing bounded record algorithm with the S7D U-Boot APIs and
board-selected MMC device. Arm and service the Meson watchdog, durably record
an attempt before handoff, load the selected kernel FIT from SYSTEM, require
its embedded public key and pass the selected deployment ID to native init.
Remove the old MOS cfgload/raw-slot boot and installer hooks from this path.
Retain vendor recovery primitives needed to install/recover the new bootloader.

Stage the content certificate in the kernel source, force the agreed command
policy, build the early storage/verity/watchdog requirements in, and preserve
the existing display and peripheral inputs. Derive FIT load/entry/DTB/initramfs
addresses and bootm capacity from the board memory map and built payload sizes;
CX3576's addresses are not valid defaults for this work. Verify the final control
DTB containing the required key actually reaches the exported Amlogic FIP.

Verification: final configs and exported key checks; wrong-key, unsigned and
modified FIT refusals; torn-record writes and three-trial fallback tests;
watchdog failure before attempt consumption; console entry without a trial.

### 3. Connect packaging, runtime and peripherals

Add minimal S905X5M board and radio-userland package producers/manifests using
the current package contract. Firmware and kernel modules belong in signed
kernel support; scripts, units and configuration belong in root packages.
Package optional front-panel files with correct executable permissions, and
preserve independent Wi-Fi/Bluetooth selection and their shared SDIO transport.

Use DATA/state/bluetooth for the derived controller address and pairing keys,
ordered with whole-/var mounting and seeding. Match regulatory.db/signature to
the S905X5M built-in trust store and arrange reload after support is available.
Reuse the concurrent regdb validation mechanism without adding unverified keys
or weakening signature checks. Do not duplicate the shared var implementation.

Extend the existing component CLI, image producer, verifier and Rust backend
with explicit board facts for FIT memory, DTB, watchdog, native record offsets
and Amlogic firmware identity. Add an authenticated, bounded Amlogic firmware
artifact/receipt contract; distinguish the vendor-framed hardware boot area
from the selected SD/eMMC system disk when validating readback. Keep bootloader
maintenance separate from ordinary root/kernel updates. No arbitrary raw-write
range or generic user-supplied hardware destination is introduced.

Verification: RED then GREEN for unsupported board/backend and bounded target
contracts; package selection and radio-decline fixtures; support trust checks;
Bluetooth mount ordering and optional front-panel checks; existing board suites.

### 4. Produce and qualify the development artifacts

Build from a recorded snapshot containing the current shared changes and this
port. Produce the MOS U-Boot/recovery artifact, kernel/support and root components,
signed deployment/update archive, and timestamped complete SD image with hashes.
Update the existing board README, U-Boot README, dossier and current entry points.
Keep `BOARD_RELEASE_TARGET=0` until current hardware qualification is recorded.

Verification: focused tests followed by `make os-build-test`, `make os-verify-test`,
`make os-rootfs-manifest-test`, `make os-fit-records-test`, affected Rust gates,
package ownership/preflight, shell/host-toolchain checks and `make docs-verify`.
Run image/signature negatives and real DATA-only growth with protected-range
sentinels. Shared ARM64 QEMU results cover native userspace only. Physical S7D
acceptance separately requires new-firmware boot, serial/HDMI, Ethernet, USB,
Wi-Fi, Bluetooth, /var persistence/quotas, update/fallback and shutdown evidence.

## Risks

- S7D uses a vendor U-Boot fork and Amlogic boot framing. Required FIT verification
  and key embedding must be proved on the exported artifact, not inferred from
  a successful generic tool invocation.
- SD system boot still depends on the installed MOS firmware in eMMC. The
  historical unsigned SD bridge cannot qualify the current trust contract.
- Vendor calibration/environment writes, shared SDIO rail ownership, kernel
  memory reservations and watchdog handoff need board-specific verification.
- This checkout has concurrent storage/regdb work and scratch producer collisions.
  Isolated snapshots must preserve the requested current changes and their hashes.
- No current device access or new boot log is supplied; hardware tests remain
  unqualified until actual bench results are available.

## Scope

`boards/s905x5m/`, directly shared FIT packaging/records, affected `build/` and
`verify/` paths, `pkgs/mos-deploy/`, package selection, relevant tests/CI and
existing board documentation. PMA + pma-bun + pma-rust apply; use pma-cr after
implementation. No dependency upgrades, unrelated UI/API changes, compatibility
readers, old data migration, automatic flashing, commits or pushes.

## Alternatives

A BSP-only update would fix kernel build inputs but leave no usable current MOS
image. Reviving RAUC/cfgload would restore the retired contract and is rejected.
Implementing both SD and complete eMMC installers together is possible but adds
vendor package/install recovery acceptance; the user's delivery preference can
expand this proposal before implementation.
