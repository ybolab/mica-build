## The pane

The `/network` pane was a `dhcp`/`address`/`gateway`/`dns` form per interface
over untyped JSON. It now parses the subtree into `mosd_settings` types, one entry at a time —
`fn parse_network(network: &Value) -> (NetworkEntries, Vec<String>)`
(`os/pkgs/mosd/apid/src/routes.rs:1933`) and renders a kind control plus the
parameters of all four kinds, filled in from the stored entry —
`fn kind_fields(kind: IfaceKind, cfg: Option<&IfaceSettings>) -> Markup`
(`os/pkgs/mosd/apid/src/routes.rs:2033`). Four groups are rendered at once
rather than one per selected kind, because this pane ships no JavaScript and a
group that only appeared after a reload could not be filled in on the same
visit; the handler reads only the group the submitted kind names, which makes
the reconciler's *"is kind X but carries a Y block"* rule unreachable from this
path rather than merely checked on it, in
`fn iface_settings_from_form(`
(`os/pkgs/mosd/apid/src/routes.rs:1045`).

Peers are a list of records, so they get the shape the SSH pane already uses for
one: an add form and a per-entry remove control, posting to
`/network/peers/add` and `/network/peers/remove`, keyed by the peer's public key
the way a stored SSH key is keyed by its fingerprint, in
`fn peers_markup(iface: &str, wireguard: Option<&WireguardConfig>) -> Markup`
(`os/pkgs/mosd/apid/src/routes.rs:2088`). Those two routes write the peer list
at its own dot-path, `fn peers_settings_path(iface: &str) -> String`
(`os/pkgs/mosd/apid/src/routes.rs:2002`); the interface
form writes the whole entry and carries the stored peers forward, because a
save that dropped them would disconnect every far end and report *"Settings
saved."*

### The echoes

apid re-states the reconciler's cross-field rules before writing, and it is
explicit that this is an echo and not a second boundary: *"Echoed and not
forked"* (`os/pkgs/mosd/apid/src/routes.rs:1195`) — `validate_network` still
runs on every apply, including the applies that never went through apid, and
this runs first only so the operator reads which field is wrong instead of a
502 from a failed bus call. The check runs over the **candidate** tree rather
than the one entry being written, because every relational rule is about two
entries at once: editing `eth1` to take an address is refused when `br0` claims
it as a port, which no check confined to `eth1` could see —
`fn validate_entries(entries: &NetworkEntries) -> Result<(), String>`
(`os/pkgs/mosd/apid/src/routes.rs:1205`).

The peer rules are echoed the same way, and they keep the reconciler's own
discretion about what an error may say: *"A rejected peer is named by its index
and never by its key"* (`os/pkgs/mosd/apid/src/routes.rs:1165`), because an
operator who pasted a private key into that field must not find it on the page
that refused it. A test asserts exactly that.

Three predicates are copied rather than called — `is_ip_or_cidr`, `is_host_port`
and the 32-byte base64 key test,
`fn is_wireguard_key(value: &str) -> bool`
(`os/pkgs/mosd/apid/src/routes.rs:1158`). mosd
is a binary crate, so apid cannot call into it, and moving the predicates into
`mosd-settings` would have edited the reconciler, which M5 closed. Each copy
names its source line and the reason the tree already accepts the duplication:
*"apid validates the address on its write path, but the settings file is
writable without apid, so the boundary must hold here"*
(`os/pkgs/mosd/mosd/src/reconciler/network.rs:294-296`).

## The rotate route

`POST /api/v1/actions/wireguard/{iface}/rotate-key`, composed from the leaf
`"/v1/actions/wireguard/{iface}/rotate-key"`
(`os/pkgs/mosd/apid/src/routes.rs:250`), declared POST-only —
`.route(V1_WIREGUARD_ROTATE_ROUTE, post(api_v1_wireguard_rotate))`
(`os/pkgs/mosd/apid/src/routes.rs:292`) for the reason the power and SSH
mutations are: nothing that merely follows a link may replace a tunnel's
identity. It calls `rotate_wireguard_key`
(`os/pkgs/mosd/mosd/src/bus.rs:770`) and answers the new public key from
`pub(crate) async fn api_v1_wireguard_rotate(`
(`os/pkgs/mosd/apid/src/routes.rs:605`).

The interface name is passed to mosd unexamined. mosd owns the rule — a
declared entry of kind `wireguard`, `InvalidArgs` for anything else — and apid
classifies that through the same §2.4 table the read routes use, so the refusal
is a 422 `settings_rejected` naming `network."<iface>"` as the dot-path at
fault. A second copy of the rule in apid could disagree with the first.

The gate needed one addition, and its shape is the interesting part.
`is_declared_api_route` hands a path off to the route that answers for itself,
and it must hand off **exactly** what the router serves. The rotate predicate
therefore releases an empty interface segment — *"An *empty* segment is
released, unlike [`resource_dot_path`]'s empty"*
(`os/pkgs/mosd/apid/src/routes.rs:320`) — because axum's `{iface}` matches zero
or more characters where `{*path}` matches at least one, so
`.../wireguard//rotate-key` is a path this router really serves. Refusing it in
the predicate would answer the gate's redirect where the route answers §2.4's
envelope, and a client that followed a 303 from a POST would land on `GET
/login`, read 200 and believe it had rotated a key. Found by a test that
asserted the opposite and was wrong.

There is deliberately **no rotate control on the pane**. The design places the
rotation on the API and classifies it *"additive | new route"*
(`docs/task/RFCT-200.md:517`) and section 8's M6 cut asks
for *"rotate-key route"* (`docs/task/RFCT-200.md:596`) and not a pane button;
adding one would be a second surface for one action with no ratified shape. The
pane says what the API is for instead.

## Redaction

`privateKey` joins the denylist —
`const SECRET_FIELDS: [&str; 5] = ["psk", "passwordHash", "password_hash", "hash", "privateKey"];`
(`os/pkgs/mosd/apid/src/redact.rs:33`). It
redacts nothing: no shipped schema has such a field. That is the point, and the
constant says so — *"It is the fail-closed half of that rule: the day a field of
that name appears anywhere in either tree, it is already covered"*
(`os/pkgs/mosd/apid/src/redact.rs:30-31`).

The existing denylist tests are driven from the failing side — they require the
fixture to carry every name on the list, so an entry nobody planted a value for
fails rather than passing vacuously. The settings fixture therefore grows the
hypothetical the entry guards against, a `network.wg0.privateKey` that no
reconciler could produce, and the test set grew a third subtree to read it from.

## Live-state readers

The two fields M5 publishes are read in both places M6 owns. The pane renders
the kind, the unit file name and, for a tunnel, the public key —
`fn live_state_markup(view: &NetworkView, iface: &str) -> Markup`
(`os/pkgs/mosd/apid/src/routes.rs:2069`), and says what is *not* there: *"The
private half is on this device in a file only systemd-networkd can read. It is
never shown here, never in the API, and there is no route that returns one."*
(`os/pkgs/mosd/apid/src/routes.rs:2079`). The JSON surface needed no code —
`GET /api/v1/state/network` is a passthrough of what mosd published,
`entry["publicKey"] = json!(self.keys.ensure(iface)?);`
(`os/pkgs/mosd/mosd/src/reconciler/network.rs:670`) — so what M6 adds there is
the assertion that it carries `kind` for every entry and `publicKey` for the
tunnel, and no `privateKey` for anything.

## OpenAPI

The document is generated from the handlers and committed, and CI asserts the
two agree: *"The committed OpenAPI document is what the shipped flag prints"*
(`.github/workflows/check.yml:186`). It was regenerated with the command that
step names, `cargo run -p apid -- --openapi > apid/openapi.json`, so the
committed bytes are the flag's output rather than a hand edit; `apid`'s own
test asserts the same thing without CI.

One trap is worth recording because it is invisible in review: `utoipa` copies
a handler's doc comment into the published document, so an intra-doc link in it
becomes an apid symbol name in front of every client. The link is prose:
*"Prose and not an intra-doc link to the classifier"*
(`os/pkgs/mosd/apid/src/routes.rs:588`). This is the HTTP twin of the zbus trap
RFCT-204 records for method doc comments.

a changed code on an existing failure, so the one §2.1 item the CI diff cannot
mechanise is not engaged either.

## Deviations and forced changes

1. **DHCP off with an empty address stopped being a 422.** It is now an
   interface with no addressing at all, and the comment states why it had to
   change: *"It used to be one, and it stopped being one when bridges became
   expressible"* (`os/pkgs/mosd/apid/src/routes.rs:952-953`). A bridge port must
   carry neither `dhcp` nor `static`, and it must already be a declared entry
   before a bridge may name it, so the old rule made a bridge unbuildable
   through the pane in either order: creating the port first was refused by
   apid, and creating the bridge first was refused by the reconciler. One row of
   an existing test moved from the rejection list to a positive test of its own.
   An address that is present and not a CIDR is still refused.
2. **One quoted literal in `docs/design/api.md` was corrected.** The document
   quotes the denylist constant verbatim, and the constant now has five names;
   the quotation and the sentence that counts it were updated in their own
   commit. This is a forced value change, not the M8 documentation pass:
   `api.md` also still said, at this milestone's commit, that *"The
   `/api/v1/actions/<verb>` root does not exist"* (`docs/design/api.md` §2.2),
   which this milestone makes false and which M8 owns. It is flagged here
   rather than fixed here. RFCT-207 rewrote that sentence, so the quotation
   above is of what the document said then; the line citation it carried is
   dropped rather than re-pointed, because no line of today's `api.md` says it.
3. **Citation line numbers were re-anchored, numbers only, in their own
   commit.** The apid edits shifted 287 citations across `docs/design/api.md`,
   `docs/design/bus.md`, `docs/design/remote-management.md` and
   `docs/task/RFCT-200.md`. The mapping was computed from the pre-image with a
   throwaway line-correspondence pass, not by hand and not by re-reading the
   prose, so no claim moved with its number.

## Decisions worth naming

1. **Peers are edited by add and remove, not by a text field.** A list of
   records has one existing shape in this tree — the SSH key pane's — and
   reusing it costs two routes and teaches the operator no new notation. The
   alternatives were a JSON textarea (the tree's own spelling, but the only
   untyped control on an otherwise typed form) and a positional line format
   (a grammar invented for one field). Removal is keyed on the public key
   because it is a stable handle that is public by definition, so it sits in a
   hidden field without putting anything secret on the page.
2. **The interface form carries the peers forward rather than rendering them.**
   The save form has no peer inputs, so the handler reads the stored list at
   submit time and writes it back inside the entry. A hidden field would be a
   list two browser tabs could fight over.
3. **An entry whose body does not parse is named, not hidden and not fatal.**
   The subtree is parsed per entry, so one hand-edited body cannot blank out
   every other interface's form; the unreadable name gets an error box and no
   form, because a form rendered from a body this code could not read would
   write back a guess.
4. **No VLAN id bound.** networkd's range is narrower than `u16`, and the
   reconciler renders the id straight out of the `u16` without a range test —
   `"[NetDev]\nName={iface}\nKind=vlan\n\n[VLAN]\nId={}\n",`
   (`os/pkgs/mosd/mosd/src/reconciler/network.rs:566`), so a bound invented
   in apid would refuse a tree the boundary accepts. The echo is an echo.
5. **The e2e phase builds a tunnel and not a VLAN or a bridge.** Stated in the
   phase itself: *"It builds a **tunnel** and not a VLAN or a bridge,
   deliberately."* (`test/apid-api/src/phases/05b-wireguard.ts:11`). A VLAN
   needs a declared parent and a bridge enslaves a declared port, and the
   guest's only interface is the one every assertion travels over — the hazard
   05-mutate already refuses to take. The VLAN and bridge controls are still
   asserted as markup and as 422 echoes, which is everything checkable without
   taking the link.

### Why the e2e suite was not run, and what was run instead

`make os-apid-api-test` *"IT BUILDS NOTHING and assumes
`_out/x64/x64-mos-v2-latest.img` already exists"*
(`Makefile:333`). No such image exists anywhere on this host and no `_out`
directory exists in any checkout of this repository on it, so the harness has no
guest to talk to. Producing one is not a step this milestone can absorb: it
needs the rootfs stage chain and the dev signing keys built from scratch, and
the image line is M7's.

A second reason is worth recording, because it would survive the image being
built. Phase `04-readonly` encodes the contract of the image it was written
against, and that image predates the `/api/` routes: it lists `/api/versions`
among the targets that *"Targets that must all produce `api_not_found`'s envelope."*
(`test/apid-api/src/phases/04-readonly.ts:100`) and asserts an unauthenticated
`/api/versions` is a 303 to the login page. Today's tree serves it 200
unauthenticated by design, which `apid`'s own
`api_versions_answers_the_served_set_without_a_session` asserts in process. The
phase's own image-skew guard says the same thing about `/mqtt` and names the fix
it needs. So a run against a freshly built image goes red on assertions that
belong to whoever rebuilds the image, not to this milestone, and those
assertions were left alone: rewriting them blind — against an image that cannot
be booted here to check the rewrite — would replace a visible skew with an
invisible guess.

What was run instead, on the host, against the suite as committed:

| check | result |
| --- | --- |
| `bun run typecheck` (`tsc --noEmit`) over `src/`, the new phase included | clean |
| `bun run selftest` — the harness's own suite | `RESULT: PASS (37/37 checks)` |
| the phase registry, exercised through `runPhases` in a throwaway script | `01-transport -> 02-setup -> 03-login -> 04-readonly -> 05-mutate -> 05b-wireguard -> 06-backoff -> 07-reboot -> 07b-postreboot -> 08-poweroff`, no duplicate ids, no empty `assumes`, and the unknown-phase refusal still fires |

The new phase's assertions are therefore reviewed and type-checked but **not
measured against a device**. That is the honest state of this gate, and it is
the one thing in this milestone that is not evidenced by a run.
