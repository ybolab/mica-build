# 设计：调试与运维访问

> [English](../../design/access.md) | 中文

## 0. 状态标记怎么读

- **[已实现]** —— 代码存在，且能按路径点名。
- **[部分]** —— 一部分存在；缺的那部分会被点名。
- **[未实现]** —— 刻意地一行代码都没有，只有文字。
- **[已决策]** —— 曾经悬而未决的问题现已由用户拍板。它标记的是**决定**而非代码状态：
  一节完全可以同时是 **[已决策]** 和 **[未实现]**。

为什么设计文档需要这套纪律：**死代码还有编译器、测试和"grep 调用方"能把它暴露出来；
而一个只以文字形式存在的安全控制，没有任何机制会发现它其实不在。**
一段没有日期的设计文字描述了某个控制，并不构成该控制存在的证据。

无标记的章节陈述的是原则、偏好或历史，而不是机制。

## 1. 原则

- 访问通道是**模型层之下的一等服务**（设置子树 → 协调器 → 服务），**绝不是绕过模型层的旁门**。
  执行者是 mosd，经由 systemd。
- **配置下发和调试是两个不同的问题。** 弱认证、资源白名单的向导负责"现场没网"；
  强认证的完整 shell 负责深度调试。用一个万能 shell 同时干两件事，
  必然把认证强度拉低到"够用就行"的水平。
- **"关闭"必须有三种强度**（见第 5 节），最强的一种是**编译期就不存在**。
- **活得比它所服务的会话更久的凭据是一种负债。** 持久访问靠密钥；口令是例外，而且是临时的。

## 2. 通道

| 通道 | 能力 | 认证 | 可用性 |
|---|---|---|---|
| 网络向导（tty2 TUI；AP 强制门户；经 kiosk 的 HDMI 本地向导） | 仅白名单内的网络资源；无密钥、无执行、无原始日志 | 每设备 PIN | **未实现** |
| SSH（**OpenSSH**，由 mosd 驱动） | root（`mos` 并不是一个更低的权限层级） | SSH 公钥，持久；可选**临时** root 口令 | **prod 与 dev 都发布**，且**两者都默认关闭** |
| 控制台 shell（tty3） | root | 同 SSH | `access.console.shellEnabled` 在 schema 里有，但**没有任何协调器消费它** —— **未实现** |
| 串口控制台（`serial-getty@ttyFIQ0`） | 只有登录提示符 | `/etc/shadow`，即默认什么都不接受 | **存在** —— 由 systemd 的 getty-generator 依据内核 `console=` 参数在两种 profile 上拉起。**它没有任何会接受凭据的账户**，见第 9 节 |
| 救援（所有槽位失败时的 FIT 入口） | chroot 修复环境 | 物理接触 | **未实现** |
| 工厂（rockusb / SoC loader 模式） | 整盘重刷 | 物理接触 | 硬件层面，见 9.2 |

**只有一个策略源。** 镜像携带 **OpenSSH**，而 mosd 渲染**唯一**那个配置它的 drop-in 并驱动
`ssh.service`。这份归属权正是让 sshd 策略保持单点的原因：**不存在第二份由运维手改的
`sshd_config` 让设置树去和它漂移。**

## 3. 配置模型 —— **[已实现]**

由设置树模型、sshd 协调器和临时口令模块共同实现。

**`listenAddresses: []` 的含义是"监听全部地址"**，不是"不监听"——这是空列表容易被读反的地方。

尚未建模的部分（更细的能力划分、向导通道的配置）标记为 **[未实现]**。

## 4. 认证

**浏览器管理会话 —— [已实现]。** 内建 SPA 和自定义 SPA 都是 `/api` 的客户端。
`GET /api/v1/session` 查询状态，`POST` 用管理员口令登录并建立
`HttpOnly; Secure; SameSite=Lax` 会话，`DELETE` 撤销会话。登录返回的随机 CSRF 值只保存在
页面内存中；凡用 cookie 发起写操作，都必须把它放进 `X-CSRF-Token`，否则统一返回
403 `csrf_invalid`。程序化 bearer token 不受这条 CSRF 规则影响。

**当前阶段 —— [已实现]。** 持久访问靠 SSH 公钥；root 口令是**临时**的，由 mosd 在运行时设置。

请求边界先完成 bcrypt 与 shadow/marker 写入，再把一个 `access.ssh` 应用任务放入队列；
队列里从不出现明文口令。apid 返回 202 + task id，HTML 表单则跳转到
`/ssh?task=<id>`。服务端渲染页面在 queued/running 时用 meta refresh 刷新，并在
succeeded、failed、interrupted 或有界历史已经找不到该 id 时停止；不引入 JavaScript，
也不再让一次口令提交把浏览器留在无上界的空白等待中。

**已废止的模型。** 早期的"每设备口令"模型曾把口令写进 `/etc/shadow`，但**系统从未把这个口令
暴露给运维**——所以那条路径当时就已不可用。当前设计只是让它**诚实地**不可用，
而不是关掉了一扇本来能用的门。

**后续阶段 —— [未实现]。**

## 5. 分层关闭

### 5.1 运行时 —— **[已实现]**

`enabled: false` → 协调器停止并在运行时禁用 `ssh.service`。可逆，且是默认值。

### 5.2 META 锁定 —— **[未实现]**

设计意图：META 分区里的一个单向位；一旦置位，管理面就忽略配置、永不注册这些服务。
只有整盘擦除才能清除它——但**工厂重置刻意不清除它**："忘了密码"应当可以自助解决，
"解开 shell 锁"不行。

**以上全都不存在。** 在本仓库所有 `.rs`、`.sh`、`.conf` 中 grep `lockdown`，`docs/` 之外一无所获。
没有单向位，没有东西读它，也没有任何重置会保留它。

**而且工厂重置本身也没有实现。** 树里没有任何东西执行它。所以这一段描述的是
**一个没人能触发的重置，去保留一个没人能置位的位**——这恰恰就是第 0 节的标记纪律存在的理由。
这个锁定到底要不要做，是一个悬而未决的产品决定。

### 5.3 镜像 profile —— **[部分]**

今天发布**两种** profile，在构建时选定并记录进镜像。`/usr/lib/mos/profile.conf` 携带
`MOS_PROFILE=dev` 或 `prod`，模式 0444。它放在 `/usr/lib` 而不是 `/etc`，因为它描述的是**镜像**
而不是设备——这也把它放进了只读的 verity 根里，**使得生产设备无法被改成开发设备**。

**两种 profile 现在都把 `access.ssh.enabled` 播种为 false**，两种镜像都不启用 `ssh.service`。
所以 profile 目前在 SSH 这件事上不选择任何东西。之所以仍然保留 `Profile`，是因为它
**失败即关闭**的解析本身是承重的：文件缺失、路径不可读、键拼错、值为空、值无法识别，
**全部解析为 `prod`**；而且比较是**大小写敏感**的，所以 `DEV` 也解析为 `prod`。
构建会拒绝任何不是小写 `dev` 或 `prod` 的值。

`ROOT_PASSWORD` 构建参数**仅存在于 v1**。v2 的打包阶段会**无条件地**让任何"工厂 shadow 里
存在可用哈希"的构建失败——对每个账户、在两种 profile 上都如此。**因此 v2 烤入 root 凭据是
不可构建的，dev profile 也不例外。**

**缺失的部分（所以是"部分"）**：`sealed`——那种"无 shell"本身构成签名镜像身份一部分的
完全无 shell 构建——**未实现**。

**随 prod 决定一并接受的取舍**：对 `prod` 而言，编译期不存在这层保护已经不再守护 SSH；
实际的防线是默认关闭的配置、仅密钥的持久认证，以及——等它们存在时——META 锁定与审计。

曾提出四项意图，现在**两项有代码有测试，两项没有**，而说清楚哪两项是哪两项正是本节的意义。

## 9. 恢复：运维把自己锁在外面之后

### 9.1 没有任何软件路径能回去

一个同时丢失了 webAdmin 口令**和**全部授权密钥的运维，**没有任何软件路径能回到这台设备里**。
穷尽地讲：

- **apid** 是唯一能启用 SSH、添加密钥或设置口令的东西，而它需要 webAdmin 凭据。
- **SSH** 是关的；即使打开，它也只接受一把并不存在的密钥。
- **串口控制台存在、可达，并且没有任何入口。** 这点要说精确：systemd 的 getty-generator
  **确实**会在两种 profile 上依据内核 `console=` 参数拉起 `serial-getty@ttyFIQ0`，
  登录提示符**会**出现。但它没有任何会接受凭据的账户——root 被锁定，
  其他每个账户都被 shadow 协调器锁定。

### 9.2 整盘重刷能恢复什么 —— **[已实现]**

v2 镜像是一个**携带全部十一个分区的整盘镜像**，并为 META、STATE、DATA 构建全新的 ext4 文件系统。
经 rockusb 刷写因此会替换这三者：STATE（凭据与身份）、META（一体机与更新元数据）、
DATA（运维的 `/home`、`/root` 及 `/srv` 下的一切）。

**有一处精确性绝不能被抹掉。** DATA 在首次启动时会增长到超出所刷镜像的范围。
之后的一次重刷只写镜像自身的范围和一张全新的 GPT，所以**超出该范围的块仍留在磁盘上，
只是新文件系统不再引用它们**。这里的"清除"意思是**通过新文件系统不可达，而不是已被擦除**。
要处置设备或把设备转手给别人的运维，需要知道这个区别，**应当擦除介质而不是重刷**。

## 10. 持久化模型：走设置树，而不是可写的 `/etc`

**用户已决策：方案 A。没有 `/etc` overlay，将来也不会有。** 配置**经由设置树**持久化；
确实需要手改文件的服务，会拿到一个**刻意设置的 bind mount**。

- **10.1 未建模的设置就是不受支持的设置 —— [已实现]。** 运维需要持久化的任何东西，
  都必须在设置树里建模。
- **10.2 确实必须手改文件时**：新增一个 bind —— **[已实现]**。
