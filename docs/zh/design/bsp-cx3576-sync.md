## 0. 为什么它是独立文件，而不是 boards.md 的一节

两个理由，都是结构性的。

`design/boards.md` 是**跨板卡的 BSP 契约**——产物接口、内核配置断言、新板卡清单。
它讲的是任何一块板必须提供什么。而「某一块板同步到了上游哪个提交」是另一种文档，
塞进一份契约里会很别扭。

更重要的是：`docs/verify-index.sh` **双向**断言 `docs/design/*.md` 与 `docs/README.md`。
**一个文件因此获得了一条常设断言**，保证它仍然存在、仍然能从索引到达。
一个已被索引文件内部的**小节**则什么都得不到——而那正是这份记录要防的腐坏。

**不要靠 diff 两棵树去重新推导共同点。**

**「同步到 `5e2b1c3`」这句话主张什么**：截至并包含 `5e2b1c3` 的每个上游提交都已被审阅，
其中适用于 mos 的都已移植。为使这个主张**可核查而非仅是断言**，
四个被审阅的提交（两个有实质工作、两个没有）的处置都记录在英文版的表格里。

**重新核对一个空操作很便宜**：`git -C <upstream> show --stat <sha>`。
未来某次同步若不同意上面某条处置，**应当说出来**，而不是默默地重新移植一遍。

**这一行怎么维护**：执行下一次同步的人，在那次同步中把上面的提交与标题更新到新的上游点。
**一个陈旧的值比没有值更糟**，因为它会让下一次同步重放已经移植过的工作。

## 3. 偏离登记

这是一份**登记表，不是变更日志**。它只列出 mos **刻意**不同于上游的地方，
好让未来的同步知道**什么是不能被默默还原的**。照原样移植的东西不属于这里，git 历史已经记录了。

今天只有一条。

### D-1 —— 启动设备顺序：eMMC 先于 SD

| | |
|---|---|
| **位置** | uboot patch 里 `rk3576-generic.dts` 的 `bootstd` 节点 |
| **上游是** | `bootdev-order = "mmc1", "mmc0", "usb";` —— SD 优先，插入的 SD 卡会覆盖 eMMC |
| **我们是** | `bootdev-order = "mmc0", "mmc1", "usb";` —— eMMC 优先，SD 次之，USB 最后 |
| **理由** | 用户于 2026-08-20 决定 |
| **守卫** | uboot 的 Dockerfile 对**编译后的**设备树断言 `bootdev-order` 等于 `mmc0 mmc1 usb` |

**SD 是被保留为回退，而不是被移除**：eMMC 起不来时救援 SD 仍然能引导，
但它无法覆盖一块能正常引导的 eMMC。

这条被记录为**一个决定**，而不是从威胁模型或安全论证推导出的结论——它本来就不是。
**把它记录为决定，正是让它可以被有权推翻的人推翻。**

守卫跑在编译后的设备树上，所以未来某次同步若默默恢复了上游顺序，会在**构建时**失败，
而不是在客户桌上的**首次启动时**失败。

### D-1 单靠设备树在运行时是强制不了的

U-Boot 的 `bootstd_get_bootdev_order()` **先读 `boot_targets` 环境变量**，
一个非空的值会**整个替换掉**设备树里的 `bootdev-order`，而不是与之合并。

在调试变体上这咬不到人——它的环境是 `ENV_IS_NOWHERE`，什么都不持久。
**但在 mos 的 A/B 变体上它能咬**：那个构建在 eMMC 里存放持久的冗余环境，
所以一个由 `saveenv`、由旧镜像、或由人在 U-Boot 提示符下手写的 `boot_targets` **能挺过重启**，
在出厂产物上**悄悄恢复某个别的顺序**——而上面那条构建期守卫**仍然通过**。

因此 `BOOTCOMMAND` 在**两个**阶段都以 `setenv boot_targets` 开头，
在任何东西读取顺序之前先清空它。这次清空是**每次启动的、非破坏性的**：
它不带值、也不执行 `saveenv`，所以不会改写已存储的环境。
每个阶段确切的 `BOOTCOMMAND` 字符串都被单独断言，所以**丢掉这次清空无法静默通过**。

这是一条机制说明，**不是第二条偏离**：上游也带同样的 `setenv boot_targets`。
它记在这里，是因为它对 mos 之所以重要的**理由**与对上游不同，
也因为**没有它，D-1 就是一条运行时值可以覆盖的性质**。
