# 设计：无网络配置（Provisioning 模型）

> [English](../../design/provisioning.md) | 中文
>
> 在不能假定有网络的情况下，一体机如何获得并改变自己的机器配置。

## 1. 与上游的分歧

mos 一体机必须在**零外部输入**的前提下到达完全可用的状态——这不同于数据中心机器，
后者可以无配置启动、然后从网络上等一份配置下来。分三层实现。

## 2. 第一层 —— 首次启动自配置（已发布）

当 STATE 上没有配置时，设备自己生成一份、持久化它，此后就是一台完全可用、可配置的一体机。
mosd 在**加载设置存储之后、第一次协调之前**执行这一步，所以第一次协调看到的已经是播种后的树，
而不是内置默认值。

从空的 STATE 出发，首次启动恰好写出一个 `settings.toml`，外加第 3 节所述的两个密钥文件：

- **主机名 `mos-<deviceId 前 8 位十六进制>`**
- **`provisioning.deviceId`** —— 16 字节 CSPRNG，表示为 32 个小写十六进制字符
- **`access.device.passwordHash`** 与 `generation = 1`
- **`access.ssh.enabled`**，由镜像 profile 播种
- **`provisioning.state = "complete"`**、`seededGeneration = 1`
- `network` **留空**，`wifi` 保持 schema 默认值

### 「不需要网络」这个性质，以及它是怎么被保证的

这是第一层的**目的**，不是它的副作用。一台一体机在工作台上开箱，没有 DHCP 服务器、没有 DNS、
可能连线都没插，它依然必须到达一个有名字、有凭据、可配置的状态。

- **主机名从设备身份派生**，而不是来自 DHCP option 12、反向 DNS 或 MAC 地址。
  除了去掉网络依赖，这还让名字**稳定**：设备换网段、租约过期、换网卡，名字都不变。
  8 个十六进制字符是 32 位，同一个局域网内碰撞不是实际问题，而且短到可以印在标签上。
- **该模块根本不引用任何网络 API** —— 它的全部 import 只有 `std::fs`、`std::path::Path`、
  `anyhow`、`mosd_settings` 和 `crate::identity`。这是一个**关于源码的、可机械检查的断言**；
  它**不是**"该进程不发出网络系统调用"的证明，而且没有任何单元测试能建立后者。
- **`network` 是刻意留空的。** 镜像本身已经带了一份匹配 `eth*` 的静态 `80-dhcp.network`，
  所以新设备上 DHCP 不用播种就能工作。播种反而意味着**猜接口名**——在一块网卡枚举为 `end0`、
  甚至根本没有以太网的板子上写下 `network.eth0`，只会为一个不存在的接口生成 networkd unit。
  留空也让 mosd 的网络协调器**不去主张一个运维从未配置过的接口**的所有权。
- **`wifi` 保持默认。** 此时还没有网络可加入，而是否拉起 AP 模式是上行状态机的决定，
  不是首次启动的决定。

此外还保证**原子性**（绝不出现半播种的 `complete`）与**幂等性**。

## 3. 凭据模型 —— 只在这里陈述一次

有三份文档触及这个话题，它们**全部**回指本节。这里有三处微妙之处，**每一处都已经至少被
"简化"错过一次**。

### 3.1 密钥在设备上生成，绝不在镜像里

根文件系统是 squashfs + dm-verity：只读，**在机队每一台设备上逐字节相同**，并被签名覆盖。
烤进去的凭据**按构造就是一个机队级共享密钥**，而随机生成一个又会让 verity 根哈希依赖于一次密钥生成。
所以每一份按设备区分的密钥，都是**在设备上、首次启动时**从系统 CSPRNG 抽取，并持久化到 STATE。

这一点是**被断言的**，不只是意图：有单元测试序列化一棵新建的设置树，断言文档中任何位置
都不含 `psk` 和 `passwordHash`——所以将来某个"贴心的默认值"会让构建失败。

### 3.2 有**两个**互相独立的密钥，不是一个

| 密钥 | 落在哪 | 认证什么 |
|---|---|---|
| **设备口令** | 哈希存于 `access.device.passwordHash`；明文在 `/var/lib/mos/secrets/device-password`（0700 目录下的 0600 文件） | **什么都不认证**（见 3.6）——不认证 SSH、不认证本地控制台、不认证 apid 管理界面 |
| **AP PSK** | 明文在 `/var/lib/mos/secrets/ap-psk`（同样权限） | 加入配置用接入点的 WPA2 客户端 |

两者都是从系统 CSPRNG **独立抽取**，`deviceId` 也是。**没有任何东西派生自主机名、MAC、
machine-id 或时钟**：一个从"按设备区分但可猜测"的输入派生出来的密钥，只是绕了几步的机队级密钥。

**这里刻意偏离了 PLAN-008 Part D**，后者说 AP PSK"默认取每设备的配置 PIN"。两种读法都满足
"绝不是机队级常量"，所以并未违背计划的精神——但复用同一个字符串，会把两个暴露程度截然不同的
凭据耦合起来。**WPA2 PSK 紧邻广播，可以从抓到的握手包离线爆破；如果它同时就是设备口令，
那么破出 WiFi 密钥就等于交出了 root shell。** 再从 CSPRNG 抽一次不花什么成本。
有测试逐设备断言口令不等于 PSK，所以将来"简化"回一个字符串会让构建失败。

`access.device.generation` 在凭据首次创建时由 0 变 1，所以非零的 generation 意味着
"存在一份有案可查的凭据"。任何从口令派生出来的东西都必须以它作为版本计数器。

### 3.6 设备凭据今天认证什么：什么都不认证

**在当前访问模型下，没有任何东西校验设备凭据。** sshd 不、`pam_unix` 不、串口控制台不、
apid 也不——apid 一直是拿 `access.webAdmin` 去认证管理员的，从来不是拿这个。
仓库里没有任何代码路径对 `access.device.passwordHash` 调用校验器；当初为此写的那个校验函数
现在是 `#[cfg(test)]`，**正因为它在自身测试之外没有调用方**。

两半——`access.device.passwordHash` 里的 Argon2id 哈希，和 `/var/lib/mos/secrets/device-password`
里的明文——**仍在首次启动时生成、仍被持久化**。**它们是惰性的，而且是刻意保留的**：
它们被预留给后续阶段（一个支持侧凭据，或第二阶段的 PIN），而不是在改动 SSH 认证方式的同时，
连带把一个首次启动行为及其迁移一起删掉。

记录在此，是为了让下一个读者读到的是**一个决定**而不是一处疏漏，
也为了让"设备有口令"不被误读成"设备接受口令"。

## 4. 第二层 —— 本地配置通道

所有通道最终都经**mosd 总线**写入设置——**一条信任路径**，按偏好排序：

1. BOOT 分区上的配置文件（工厂或现场的离线预置）
2. USB 签名配置投放（udev 触发，厂商密钥校验）
3. AP 强制门户与 HDMI kiosk 向导
4. 有网之后经局域网用 apid
5. tty2 串口向导，最后手段

**状态。** 通道 **1 和 2 已交付**——一份配置文档，两种离线传输。通道 **4** 由 M3
交付，是有网之后操作员实际使用的那条。通道 **3** 只有 AP 强制门户的**传输层**，
门户本身还没有；通道 **5** 不存在。

贯穿五条通道的不变量：**每条通道都汇聚到同一条经过校验的写入路径——mosd 的 D-Bus 接口——
没有任何一条会绕到守护进程背后去改文件。**

### 4.0 灌入：直接写 `/mos/config/`，以及它为什么不是第六条通道

PLAN-070 §5.2 把系统配置——hostname、网络、Wi-Fi 网络、ssh 开关、broker 策略、
时间设置和更新策略——搬进了 DATA 上的 `/mos/config/`，**为的是让集成商刷完一台
设备、把配置灌进去，中间不需要任何配置仪式就能工作**。这就是*灌入*，也是整个命名
空间存在的动机。规则清单是 `docs/design/mosd.md` §5.1a；属于本页的是它相对上面五
条通道的位置。

**它不是一条通道，因为它不是一份 mosd 读取并应用的文档。**§4.1 的配置文档是一个
*输入*——一个固定名字、固定格式的文件，被解析、校验，然后经设置树写入。灌入则是设
置树本身的存储形态：集成商写的正是 mosd 本来会写的那些文档，mosd 在下次启动时把它
们当作自己的状态读取，而不是当作谁的请求。这里没有什么要应用，没有「已认领」规则
要判断，也没有状态面去报告一份文档做了什么，因为没有任何东西被消费。

**它继承、且无权选择的三条性质**（PLAN-070 §5.2.7）：

- **只在离线时进行。**灌入写在一台**没有运行**的设备上。对运行中的设备灌入是不支
  持的，理由与 §4.1.7 中没有 udev 触发的理由相同：插入介质不得重新配置一台正在运
  行的设备。
- **下次启动时按 mosd 校验自己输出的同一套规则校验。**能解析且通过校验的灌入文档
  被采纳；不能的那份会拒绝它所把守的子系统并点名该文件——解析错误不是缺席，把它当
  作缺席就是按谁也没选过的方式配置了一台设备。
- **灌进去的秘密不会被读回。**`/mos/config/wifi.json` 携带站点的 WPA2 预共享密钥，
  这正是目录 `0700`、每份文档 `0600` 的原因。灌入文档携带的任何东西都不会出现在任
  何对外记录里，规则与经 API 写入的值相同：带秘密的键要么用一个脱敏器已经携带的名
  字（`psk`），要么由引入它的那次改动把名字加上去。§4.1.7 的*无法把文档读回来*就是
  同一条性质在上一层的样子。

**灌入不继承「已认领」约束，也不应该继承。**灌入的 `ssh.json` 整个携带
`access.ssh`，`authorizedKeys` 也在内，而且在已认领的设备上照样被采纳。这不是疏漏；
两条通道立在不同的授权之上。**配置文档**（§4.1）是由站在旁边的人，把可移动介质插进
一台**正在运行**的设备，已认领拒绝规则挡住的是拿着一根 U 盘的陌生人重新配置一台已部
署的设备。**灌入**是往一台**没有运行**的设备的 DATA 分区里写，由持有存储介质的人来
做——那个人同样可以写 `/var/lib/mos/settings.toml`，把 `access.webAdmin` 的口令哈希设
成他自己选的，所以在 `ssh.json` 上加一道认领闸，等于给一栋后门就是同一个分区的房子
锁前门。**约束灌入的授权是对介质的物理占有**，就是 `docs/design/access.md` §7 已经赋
予"占有启动介质"、`docs/design/recovery.md` 赋予串口控制台的那个授权。

**状态 —— [已实现]。** 手工灌入的命名空间会被**整体采纳**：在 mosd 存在之前写进
`/mos/config/` 的文档，下次启动时按 mosd 校验自己输出的同一套规则校验，寻址树回来
时就带着它们。**解析不了**的文档只拒绝它自己的子系统、点名该文件，此外什么都不花
——规则和它背后按文档切分的覆盖范围在 `docs/design/mosd.md` §5.1a。

**最后这一点是对已交付行为的改变，值得明说。**在 F6g 之前，**任何**文档的解析错误
都会中止整次加载，于是一个打错的 `wifi.json` 会把守护进程带下去、连**网络**协调器一
起——设备为一个无关子系统的笔误而掉线。有两样东西**仍然**拒绝启动，因为它们是不同
的规则，而不是同一条规则用了两次：

- **缺失的 `/mos` 介质**（F6f）——一台读不到自己配置的设备，绝不能去渲染另一份；
- **STATE 那份文档。**它不在这个命名空间里，不能被灌入，而且携带设备身份与管理员
  凭据。把它降级成按文档拒绝，会让首次启动的自供给在真实凭据仅仅是解析失败的情况下
  重新铸一份身份和凭据盖上去，那比不启动更糟。

## 5. 第三层 —— 带机过渡层 —— 不存在

镜像流水线**没有内嵌配置机制，也没有提交任何 CA**，所以不存在一个"内嵌配置目录"让 CI 去断言它不在。
镜像校验器实际断言的是更窄、也确实实现了的一条：**发布的 `/etc/shadow` 不含可用的 root 口令**，
所以没有任何机队级凭据能进入产物。

## 6. 安全不变量

- **任何发布镜像中都没有机队共享的凭据或密钥。** 随着第三层一起，那条例外**已经消失**，
  所以这条不变量现在**无条件成立**，两个镜像校验器都断言了它的 shadow 那一半。
- **配置通道绝不绕过配置校验与审计日志。** 校验是强制的——每次写入都走类型化的设置树，
  被拒绝的写入不会改动树。**但审计日志尚不存在**，目前没有任何东西把配置或访问事件记入持久轨迹。
- **擦除 STATE 会重置配置，但绝不清除 META 锁定。** 由于 **META 锁定未实现**，
  这条不变量目前还没有东西要保护。
- **工厂重置（擦除 STATE）让设备回到未配置状态**，下次启动重跑第 2 节——包括生成**新的**设备口令
  和**新的** AP PSK。旧的随分区一起消失。**这是目前唯一存在的凭据轮换路径。**
