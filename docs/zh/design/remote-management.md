# 设计：远程管理与 API 表面

> [English](../../design/remote-management.md) | 中文
>
> 谁能触及设备、经由什么、带着何种信任——按当前代码树的实际状态，
> 外加一条**已提出但无人设计**的需求。

## 0. 状态标记怎么读

**[已实现]** 指代码存在且能按路径点名；**[未实现]** 指刻意地一行代码都没有、只有文字。
本节两者皆非。

## 1. 今天能触及设备的只有这些 —— **[已实现]**

**apid，在局域网上，走 HTTPS。** 它在 mosd 之后启动，绑定一个 HTTPS 监听器和一个**仅用于跳转**
的 HTTP 监听器，默认分别是 `0.0.0.0:443` 和 `0.0.0.0:80`。**没有第二种协议，没有第三个端口。**

**所有东西前面只有一道闸。** HTTPS 应用路由器最外层是认证闸，它依据一次性初始化或登录时签发的
会话 cookie，把每个请求导向初始化模式、登录页、或者放行。`/healthz` 和已声明的 API 路由是
**仅有的豁免**，它们自己对自己负责。

**`/api` 下的 JSON API 是只读的。** 路由器保留该前缀，其下每个未声明的路径都返回 404；
内部的每条路由都是 GET——设置读取、状态读取，外加版本发现与元数据。

**apid 不持有任何状态，它是 mosd 的客户端**，经 D-Bus 通信。它唯一的后端选择就是"连哪条消息总线"。
设置树由 mosd 持有；**apid 从不派生进程，也从不自己与 systemd 对话**。

**SSH 与控制台是访问通道，不是管理通道**，而且两者都是关闭的：SSH 在两种 profile 下都默认关闭，
tty3 的 shell 没有任何协调器消费它，串口控制台上没有任何会接受凭据的账户。

**这就是全部。** 本代码树中**没有设备发起的管理通道，也没有机队管理面**：没有任何东西向外拨号，
没有东西做设备注册，没有任何组件同时持有多台设备。**每一条入口都是入站的，都在局域网上。**

## 2. 穿透 NAT 触及设备、以及管理机队 —— **[未实现]**

设备位于别人网络的 NAT 之后。它必须能被触及以提供支持，而且一整队设备要可管理，
**同时不能开入站端口**：一台需要用户去做端口转发的一体机，等于没有支持方案；
而一台做了端口转发的设备，则背上了它主人并未选择的攻击面。

这就必然导向**设备发起**的通道——设备向外拨号，管理流量沿着设备自己打开的连接回来。

**这条需求是活的，但没有任何设计。** `docs/design/` 下没有任何文档涉及远程可达性或机队管理；
第 1 节就是这棵树的全部能力。本节**只记录这个缺口，不填补它**。任何未来设计都要先定三件事，
而且它们互相制约：

- **管理端点托管在哪、谁来运营** —— 那是一个有自己可用性故事和自己被攻破故事的服务，
  而今天它根本不存在。
- **设备如何注册**，以及吊销一次注册意味着什么。mosd 已经在首次启动时用系统 CSPRNG
  为设备生成身份与凭据，所以注册有东西可以绑定。
- **更新的定向投放如何共用这条通道。** 按设备定向和远程管理想要的是同一条设备发起的连接；
  分开决策就会产出两条。

## 3. 更新控制流

**今天成立的 —— [已实现]。** 安装是本地的，由 mosd 掌管：`InstallUpdate(bundle_path)`
把一个**已经在设备上**的 bundle 交给 RAUC。启动健康闸确认新槽位，它会先探测 systemd、mosd 和 apid；
未确认的槽位持续消耗启动额度，直到**一个无法完成启动的槽位必然耗尽额度**，引导程序随即回退。

**设备侧的拉取现在存在了 —— [已实现]，原先站在这里的那句话作废。**
`rauc-update` 和 `rauc-verify` 以 `mos-rauc-update` 随镜像交付，对着烤在同一个镜像
里的信任锚做校验（`docs/design/release-signing.md` §3.1）；apid 声明了
`/api/v1/update` 以及它旁边的 `check`、`fetch`、`install`、`mark`、`rollback`、
`reboot-override` 和 `clear-suppression`——全部经会话闸、仅 POST、留痕。这里原先写着
apid 没有声明任何更新路由；它声明了，本地的"检查/应用"面就是这些路由。

**而且设备现在会自己发起 —— [已实现]，但没有测试。**
`/mos/config/updates.json` 里的 `policy = "auto"` 让 mosd 自己检查、下载、在维护窗口
内安装，并按 `rebootPolicy` 决定是否重启（`docs/design/updates.md` §3.2）。这是第一
个会在无人看管时重启设备的能力，而它**没有任何测试**；`updates.md` §6 写明了这一点
以及它欠着什么。这与远程触发无关：那个时刻表是设备自己的，设定它的策略也是本地的。

**更新地址从哪里来 —— [已实现]。** 更新服务器的 URL 是从构建主机的 `meta/` 烤出来的
**默认值**，由一次经过认证的写入逐键覆盖到 `/mos/config/updates.json`
（`docs/design/updates.md` §2.2）。对本文档有两个后果。设备可以在不换镜像的情况下被
重新指向另一台服务器，这是服务器搬走时的恢复路线。而**一次复位会把地址还原成烤入的
默认值**——第 1 层和第 3 层都会——所以"设备在一次恢复出厂之后就不再更新了"这类工单有
一个已知成因（`docs/design/recovery.md` §2.1）。

**而且操作员现在可以从控制台把这一切设好 —— [已实现]。**
`POST /api/v1/update/config` 收一份操作员文档的 patch，走的是与其他每一次管理写入
相同的管理员授权，内置 UI 的 `AutomaticUpdates` 面板就是驱动它的
（`updates.md` §3.4）。每一次动作，无论自动还是人为，都落进同一条审计环，并带一个
点名是哪一种的 `actor` 字段（`updates.md` §3.5）。

**不存在的 —— [未实现]。** 没有远程触发，也没有机队控制面：设备之外的任何东西都无法
发起一次更新、也无法改它的策略，因为设备之外的任何东西都够不到它（第 2 节）。上面每
一条路由都是局域网入站到 apid，位于第 1 节那道凭据边界之后。

**任何未来触发器都要受的约束。** 无论更新由什么触发——策略拉取、经第 2 节通道的远程触发、
还是本地触发——都必须**汇聚到那一条更新路径**上，连同它的校验、健康闸与回滚。
**触发器是进入该路径的入口，绝不是绕过它的旁路**：一个能直接把可安装载荷塞给设备的端点，
会让"攻破该端点"等价于"攻破它能触及的每一台设备"。**自动路径是这条规则的第一次检验，
而它成立**：它走的每一步都调用手动路由调用的同一个函数，而它被剥夺的那一项能力——武装
重启门禁的覆盖——是**结构性地**被剥夺的，那个成员根本不在驱动器的接口上，而不是靠谁记
住一条规则。

**同一条规则也约束一个机队控制面能设置什么。**地址是运营决定，可以走管理通道；**信任
锚**不是，不可以。操作员文档里没有它的键，而且会直接拒绝六个锚形状的键名
（`updates.md` §2.3），所以即使一个机队控制面能写那份文档，它依然无法告诉设备该信任
什么。这就是第 4 节的凭据域不变量，落到一个机队控制面最想触及的那份文档上。

## 4. 安全态势

**今天暴露的 —— [已实现]。** apid 在局域网上，位于第 1 节那道会话闸之后，这就是**全部**入站管理面。

**今天不暴露的 —— [已实现]，而且这份"不存在"是构建断言出来的。** 没有其他入站管理端口，
没有出站管理连接，**也没有任何操作员凭据被预置进设备**。签名根文件系统在每一台设备上都是
逐字节相同的，所以烤进去的凭据就是**一个机队级共享密钥**——打包步骤会因此让构建失败，
而这条推理同样约束任何未来的机队凭据。

**未来通道必须守住的不变量 —— [未实现]。** **每个平面都是独立的凭据域，攻破其一不得在另一个中获得任何东西。**
apid 会话不是注册凭据，注册凭据不是 root shell，而持有机队通道凭据的端点**不得因此持有授权镜像的密钥**——
更新的信任锚已经是一套独立的密钥体系，并将保持独立。
