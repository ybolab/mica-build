# 制造：身份、工厂记录与隔离

本页面向把 mos 批量装到单元上的团队：谁创建设备身份和它的第一个凭据、工厂
必须保留哪些记录，以及过站失败或被重复配置的单元该怎么处理。

**先说结论，因为没有它下面每一节都会被读歪：mos 没有发布任何工厂工具链。**
发布的是设备这一半——一台在首次启动时自己铸出身份的单元、一份能把首份配置
带上去的离线配置文档，以及把镜像放上去的 loader 级烧写。把这些变成一条
*产线*所需要的东西——版本化的输入池、注入时的验证、每设备结果记录、隔离
处理、RMA 关联——都是设计好而没有建的。本页在每一节都标出哪部分是哪种，
不会把设计吹成流程。

## 1. 谁创建身份，以及谁不能

**设备自己铸出身份，工厂不提供身份。**从空 STATE 的首次启动，设备用自己的
CSPRNG 抽出 32 个十六进制字符的 `deviceId`，从中派生 `mos-xxxxxxxx` 主机名，
并铸出每设备密钥和 SSH 主机密钥——在设备上，不需要网络，绝不在镜像里。
镜像在同一发布版的每台单元上逐字节相同，这正是任何秘密都不得烤进镜像的原因。

对产线的影响是结构性的而不是流程性的：**工位无法复制、指派或复用身份，
因为根本没有这样一个输入。**工位能做的是*见证*首次启动完成，并*记录*设备
报出的 `deviceId`。这是设计中的那一步，也是未来任何工厂注入材料（设备证书、
车队身份）必须套进去的形状。

> status: shipped — evidence: `rootfs/overlay/usr/lib/mos/mos-seed-state`, `docs/design/provisioning.md`

## 2. 谁创建第一个凭据

能创建设备第一个管理员凭据的通道正好两条，产线用哪一条是本页最主要的制造
决策：

- **在最终客户处 setup。**单元以未认领状态出货；第一个访问 `/_ui/` 的人
  选定密码。工厂从不持有凭据。
- **在工厂用配置文档。**密码被写进引导分区或可移动介质上的
  `mos-provisioning.toml`，在首次启动时应用。工厂持有那个密码。

如果产线走第二条，随之而来三条规则，一条都不可选：

1. **介质就是凭据材料。**文档会被留在上面——这是刻意的，因为删除它需要在
   一次可能掉电的启动过程中以可写方式挂载操作者的文件系统。请把带着文档的
   一批卡，完全按一批印出来的密码来对待。
2. **一份文档写进一整批，就是一个密码用于一整批。**设备分辨不出它和"每台
   一个密码"的区别，也不会去试。
3. **设备在首次登录时要求轮换——而且只在那时。**由文档完成的认领会置上
   `rotationRequired`，在操作者改掉密码之前，设备拒绝每一次已认证的写操作。
   但这个约束是那次登录，不是时钟：下线后躺在仓库里的单元，其 bootstrap
   密码无限期有效。[first-run.md](first-run.md) 第 4 节完整陈述了这一点；
   围绕"过期"来规划暴露窗口的产线，规划的是一个不存在的东西。

配置文档**只在设备还没有管理员凭据时**才被应用。已经被认领的单元不能用
介质重新配置——在工厂也不行。

> status: shipped — evidence: `pkgs/mosd/mosd/src/provisioning_doc.rs`, `docs/design/provisioning.md`

## 3. 一份工厂记录必须包含什么

设计好，没有建。每台设备一份记录，在第一个工位开启，在通过或进入隔离时
关闭，并保留到产品的支持生命周期结束。它包含：

- 设备身份——`deviceId`、序列号、MAC 地址——**以从设备上读回的值为准**，
  而不是以指派的值为准；
- 该单元消耗掉的每一项版本化输入：烧写的发布版本、序列号池与 MAC 池的标识
  及从中抽取的值、标定工位的软件版本，以及任何密钥或信任锚材料的摘要；
- 每个工位的**实测值对判据**，不是光秃秃的结论。只记录了 `PASS` 的工位，
  等于没有为日后的支持工单留下任何可比对的东西；
- 最终处置：**通过**，或者**已隔离**并附上失败工位与证据；
- 对返修单元，旧身份到新身份的关联。

有两条验证规则决定这些条目的形状：没有任何东西未经验证就被注入，也没有
任何东西只由写它的那个工具来验证。镜像在首次启动前被读回并与发布版的摘要
比对；序列号或 MAC 通过*运行时*路径读回——由已启动的系统报出来——再与配额
比对。

完整要求连同每一步的负责角色，见
[../../design/manufacturing.md](../../design/manufacturing.md)。这里面的任何
一项，mos 都不提供记录格式、schema 或工位工具，也没有任何在建的工作去做它：
需要这些记录的产线自己建。

> status: unsupported

## 4. 隔离：失败与重复的配置

设计好，没有建。任何工位失败的单元**停止向前流动**。隔离意味着下面几条
同时成立：

- 记录被标注上失败及其证据，单元被**物理隔离**——留在流里的失败单元就是会
  出货的失败单元；
- **已消耗的身份值保持已消耗。**为这台单元抽出的序列号或 MAC，在该单元还
  存在期间不会退回池里。一个被"释放"的 MAC 后来出现在一台返修单元上、与
  原件并存，是一场由工厂侧造成的现场排障灾难；
- **重复的序列号或 MAC 是一次隔离事件，不是一次重试。**在读回时发现它，
  正是通过运行时路径读回的意义所在；
- 出口只有两个：**返修**，开启新的一代记录；或**报废**，以该处置关闭记录，
  并**销毁任何承载凭据的存储**。报废单元的 STATE 里明文放着秘密，因此物理
  销毁才是诚实的处置——这也是 [recovery.md](recovery.md) 第 6 节对离开
  操作者控制的单元得出的同一个结论。

**身份绝不被克隆。**不变式是：一个设备身份在整个历史上只存在于一台物理
设备上。更换的板卡拿到的是**新**身份——这一点已发布的设计本身就保证了，
因为身份是在设备上抽取的，而重刷会整体替换 STATE。没有人会把一台单元的
STATE 镜像到另一台上以"保住"它的身份；序列号的连续性在记录里处理，不在
闪存上处理。在 RMA 签收时，退回单元的凭据从收到那一刻起就按**已泄露**处理，
任何与该身份绑定的车队侧信任在签收时撤销，而不是等到诊断时。

这条不变式是本节里唯一由产品**以构造方式**（而不是靠流程）强制的部分。

> status: shipped — evidence: `rootfs/overlay/usr/lib/mos/mos-seed-state`, `docs/design/provisioning.md`

上面其余的一切——隔离记录、物理隔离、池账目、重复检测、返修的新一代记录与
报废处置——都是对产线的要求，背后没有任何工具，也没有任何计划。

> status: unsupported

## 5. 调试与恢复端口：工厂对现场

区别在于设备还不属于任何人，和设备已经承载着某位操作者的凭据与数据：

| 端口 | 在工厂 | 在现场（按发布状态） |
|---|---|---|
| 串口控制台 | 开放；工位可用它见证配置过程 | 有登录提示，且**没有任何账户接受凭据** |
| SSH / 管理面 | 工位网络与工位凭据 | 两个 profile 默认关闭；仅公钥，由操作者登记 |
| SoC loader（cx3576：rockusb） | 烧写原语 | 对物理访问开放——它**就是**恢复路径 |
| JTAG/SWD | 台架上开放 | 按板卡和版本而定；今天没有任何 mos 板卡记录或强制一个关闭状态 |

因此诚实的现场姿态是：**软件访问默认关闭且由凭据把关；物理访问按设计开放。**
这不是一个需要悄悄补上的缺口。两块 mos 板卡都站在启动保障阶梯的 I1
（`docs/design/security-model.md` 第 5 节），而 loader 端口开放正是
[recovery.md](recovery.md) 里那条恢复路径得以存在的前提。

**任何板卡上都没有发布不可逆操作。**烧断调试口、锁定启动配置或烧录密钥
哈希，在多数 SoC 上是不可逆的；而在一台恢复路径*就是*那个物理端口的设备上，
一次错误的熔丝不是让单元降级——它销毁恢复路径，可能让一整批变砖。这棵树里
没有任何东西会烧熔丝，在确切序列于同一板卡版本的牺牲件上被证明、并被写进
每一台施加它的单元的记录之前，也不允许有。

> status: board-dependent — evidence: `docs/design/manufacturing.md`, `boards/cx3576/board.env`

## 6. 一条产线今天真正能做的事

由上面各节汇总而来，设计好但没建的一律不计入：

1. 构建或接收镜像，并按镜像契约验证它（[install.md](install.md) 第 2 节）。
   开发 keyring 的镜像绝不上任何会离开这栋楼的单元。
2. 通过板卡的 loader 传输通道烧写它（[install.md](install.md) 第 4、5 节）。
3. 可选地放置一份配置文档，并接受随之而来的凭据处理责任（上面第 2 节）。
4. 见证首次启动，读回设备铸出的 `deviceId`（[install.md](install.md) 第 6
   节列出了好的首次启动长什么样）。
5. 自己保存第 1 到 4 步的记录。mos 不提供记录格式、不提供工位工具、不提供
   池管理，在第 3、4 节的工作被建出来之前也不会有。

这条流程从本仓库出发没有任何一步在物理硬件上执行过；板卡档案里每一条依赖
硬件的行都是 `not tested`。

> status: board-dependent — evidence: `docs/bsp/cx3576-example.md`, `docs/bsp/qualification.md`
