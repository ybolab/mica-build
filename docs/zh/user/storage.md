# 存储

mos 管理一套固定的、由板卡声明的分区布局；它不提供分区编辑器，并用四个
层级回答"我的数据放哪里"，每个层级都由"丢了它意味着什么"来定义。理解这
四个层级，就是操作员或集成商需要从本页获得的大部分内容。

## 1. 四个层级

| 层级 | 挂载点 | 存放 | 会扩展吗 | 何时丢失 |
|---|---|---|---|---|
| **STATE** | `/mnt/state`（绑定进 `/etc` 与 `/var/lib`） | 设备身份与状态、管理员凭据、API token、SSH 主机密钥和配对 | 否——小且固定 | 仅重刷 |
| **DATA** | 系统使用的 `/mos` 与用户使用的 `/srv` | `/mos/config/` 下的系统配置、应用数据、容器存储、UI/升级产物、操作员文件 | **是**——首次启动时占满磁盘 | 仅重刷 |
| **META** | `/mnt/meta` | 更新与设备元数据（RAUC 槽状态） | 否 | 仅重刷 |
| **EPHEMERAL** | `/var` | 可丢弃的运行时残留：日志、缓存 | 否——固定大小 | 重刷，**以及**例行清理 |

根文件系统本身是固定 A/B 槽中只读、受 dm-verity 保护的 squashfs；它从不
被写入，从不被调整大小。一次 A/B 更新只写 rootfs 和 boot 槽——上面的每个
层级都在更新中保留。

> status: shipped — evidence: `docs/design/ro-root.md`, `boards/cx3576/board.env`

## 2. 由此得出的规则

- **分开系统与用户命名空间。**系统管理的产物放在 `/mos`；集成商文件、脚本、
  应用状态和容器卷放在 `/srv`（`/home` 与 `/root` 的后端位于 `/mos`）。两个
  命名空间都由 DATA 支撑，并在重启和更新中保留。
- **想保留的东西绝不要放 `/var`。**它刻意小、被每日清理规则老化、按契约
  可丢弃——构建在有贵重物落到那里时会失败。"用了几个月然后没了"的存储，
  正是这条规则防止的失败。
- **DATA 是共享的。**容器镜像与卷、自定义 UI bundle 和应用数据用的是同
  一个分区。不做轮转就写日志的应用会饿死它的邻居；`podman system df`
  显示容器占的份额。
- **随意编辑 `/etc` 不会持久。**受支持的持久化路径是设置树
  （[configuration.md](configuration.md)）；刻意保留的 STATE 支持例外在
  设计记录中逐一列出。
- **首次启动的扩展是单向的。**DATA 在首次启动时扩展到占满磁盘；没有任何
  东西把它缩回去。重刷之后，镜像范围之外的块是不可达而非被抹除——见
  [recovery.md](recovery.md) 中的处置警告。

可写文件系统启用了周期性 TRIM，启动时的文件系统检查覆盖它们。

> status: shipped — evidence: `docs/design/ro-root.md`, `make os-repart-test`

## 3. 今天可以观察到什么

`GET /api/v1/storage/status` 一次认证读取就回答全部层级，且是**请求时观察**
而非缓存：每层给出解析后的设备、分区大小、挂载点与文件系统、已用/空闲/保留
空间（含低空间策略据以判断的百分比），以及 systemd 记录的启动期文件系统检查
结果。本板卡没有的层级会带原因报告为"不存在"，而不是被省略；正在运行的
rootfs 槽会穿过它的 verity 设备解析出来，因此不会被误报成未挂载。

读之前值得先知道三件事：

- **`/mos` 与 `/srv` 报告的是就绪状态，不是容量。**它们是同一个 DATA 文件
  系统的两个绑定挂载，字节数只在层级上计一次，两个绑定都不带容量对象；每个
  绑定报告是否已挂载、其来源是否真的是 DATA 分区，以及——对 `/mos`——写探针
  是否成功。`/srv` 从不被探测：那是操作员的命名空间，接口会把这一点说出来，
  而不是默默通过。
- **低空间压力是一个带迟滞的区间，不是一个要你去解读的数字。**DATA 与 STATE
  在已用 ≥80% 进入 `warning`、≥90% 进入 `critical`，而清除阈值更低，因此卡在
  阈值上的层级不会在两个状态之间反复跳动。
- **介质健康：设备能回答的地方做归一化，不能回答的地方明说不支持。**eMMC 磨损
  按 JEDEC 寄存器实际携带的 10% 档位区间报告——是一个范围，绝不是单一的
  "已磨损 27%"——原始寄存器值放在旁边；NVMe 与 SATA 带原因报告为不支持，因为
  本镜像不携带任何 SMART 读取工具。

fsck 结果按检查器实际的退出码原样给出，而不是折成布尔值，因为那个数字携带
"是否修复过"这一事实：0 是干净，1 表示**错误被纠正过**。没有检查历史——systemd
只保留最后一次调用，本接口也一样——没有检查单元的层级会报告"没人检查过"，而
不是读起来像干净。

设备上的常规工具仍然可用：`df` 看容量、`podman system df` 看容器在 DATA 中的
份额、journal 看检查输出；API 是操作员或集成程序**不进 shell** 就能读到的那份。

> status: shipped — evidence: `docs/design/storage.md`, `pkgs/mosd/apid/openapi.json`

## 4. 设备不会对存储做的事

没有分区编辑器。管理 API 上不存在格式化、重新分区、调整大小、挂载、卸载或
擦除操作，一旦构建长出一个，它自己的检查就会失败。除此之外，每一项存储生命
周期决定都在状态响应里被**显式回答**，而不是让人从"没有路由"去推断；今天所有
答案都是同一个：备份与恢复、离线修复、保数据的介质更换、层级的出厂重置、安全
擦除、静态加密、可移动介质，全部不支持。设计记录逐条给出理由；把其中任何一项
提升为支持，都是那份清单上的一次可见变化，而不是悄悄多出一个端点。

自 PLAN-074 起，两块板出厂的**内核**都带上了 dm-crypt 目标以及加密卷会用到的
密码算法。那是一项构建期**能力**，不是功能：没有任何卷被加密，镜像里也没有任何
能格式化或打开加密卷的工具，上面那个答案没有任何变化。之所以提前放进去，只是
因为事后再加一个内核符号要重编每一块板。请照它本来的样子读这份符号清单——静态
加密仍然**不支持**，把它提升为支持仍然是本页与
`docs/design/security-model.md` 第 6 节所描述的那个受控决定。

> status: unsupported

唯一真的会拦住操作员的存储策略是更新工作区：DATA 上留出 256 MiB 供更新使用，
当这份预留没了，安装在开始之前就被拒绝。它是**预留而非配额**——没有任何东西
统计或限制单应用、单容器的用量，检查通过之后也没有任何东西阻止应用把 DATA
写满。

> status: shipped — evidence: `docs/design/storage.md`, `pkgs/mosd/mosd/src/storage_status.rs`
