# 更新与回滚

mos 的更新是整镜像、事务性的：操作系统、其服务和所有原生应用是一个签名
产物，在设备持续运行时安装进不活动的 A/B 槽，通过重启激活，新槽无法证明
自己健康时自动回滚。没有设备上的包管理器，没有部分更新——这是设计立场，
不是缺失的功能。

配置和数据从不属于更新的一部分：设置树在 STATE 上，应用数据在 DATA 上，
安装器只写 rootfs 和 boot 槽（[storage.md](storage.md)）。

## 1. 组成部分

- **Bundle。**一个 RAUC 更新 bundle（`.raucb`）：新的 rootfs（squashfs +
  dm-verity 哈希树）和新的 boot 槽载荷，带 CMS 签名。设备在安装前对照
  自己的密钥环验证签名。由 `make os-bundle-cx3576` 构建（GRUB 分支用
  `bash build/run.sh --bundle --board x64`）。
- **槽选择。**在 cx3576 上，U-Boot 依次遍历 `BOOT_ORDER`，在冗余环境中
  维护每槽尝试计数；每次启动尝试都在内核加载*之前*扣除一次额度，因此无法
  启动的槽会在有限次复位内耗尽额度，引导加载程序回落到另一个槽。这个状态
  机由 `make os-uboot-handshake-test` 针对真实 U-Boot 二进制验证。在 x64
  上，GRUB 从 ESP 上的 `grubenv` 读取等价状态。
- **健康门。**每次启动时，`mos-health` 探测 systemd 总体状态、mosd 和
  apid，只有全部通过才执行为已启动槽补满额度的确认。失败时它刻意什么都
  不做：不确认、不补救——回滚属于引导加载程序的计数器，一个自己重启设备
  的健康门会破坏那个契约。容忍失败与阈值策略是一个配置文件，
  `/etc/mos/health.conf`。

> status: shipped — evidence: `make os-bundle-cx3576`, `make os-uboot-handshake-test`, `rootfs/overlay/usr/lib/mos/mos-health`

> status: board-dependent — evidence: `boards/cx3576/boot.cmd`, `boards/x64/grub.cfg`

## 2. 安装一次更新

设备自己发现、下载、验证并安装更新，每一步都是管理 API 上的一个路由，整份
状态只隔一次 `GET /api/v1/update`。在线流程：

1. `POST /api/v1/update/check` —— 设备镜像发布元数据，从烤进自身镜像的信任
   锚开始走完验证，并选出与本板卡、profile、渠道、设置 schema 和版本都兼容
   的目标，或者报告没有兼容目标。
2. `POST /api/v1/update/fetch` —— 有上限、可续传的下载，落在设备自己位于
   DATA 上的更新工作区里。部分下载始终只是部分：只有摘要与长度同签名元数据
   相符、并被改名进 verified 目录之后，一个 bundle 才成为可安装的。
3. `POST /api/v1/update/install` —— 把暂存的 bundle 交给 RAUC，由它验证 CMS
   签名并写入不活动的槽组。verified 目录之外的任何路径都不是可安装路径，操作
   员显式给出的 `bundlePath` 也不例外，而且这条拒绝在三处各做一次。
4. `POST /api/v1/actions/reboot` —— 激活新槽。安装进行中，以及某个应用报告
   自己不能被打断时，重启会被**拒绝**。前者没有任何手段可以解除；后者由一个
   有时限、会自动过期、双侧留痕的覆盖动作解除，而门禁的裁决与理由在按下按钮
   之前就能读到。
5. 健康门确认新槽，或者引导加载程序回滚（第 3 节）。

### 设备自己会做多少

由一个设置决定，它有三个取值：

- **`off`** —— 设备什么都不发起。上面的每一步在操作员开口时仍然可用。
- **`check`** —— 设备按周期检查（默认每天），除此之外什么都不做。它从不下载，
  也从不安装。这是默认值。
- **`auto`** —— 设备检查、下载，并**在你指定的维护窗口内安装**，随后要么停下
  等人来重启，要么在同一个窗口内自行重启。二者取其一是另一个设置，默认是等人。

**没有维护窗口，`auto` 不会运行。**选了 `auto` 却不给窗口会被拒绝，而不是套一
个默认值：因为"没有窗口"意味着"任何时候"，而对自动安装来说那读起来就是"bundle
一落地就装"。点名那个钟点，正是这个模式存在的意义。

**`auto` 从不越过重启门禁。**如果某个应用报告了自己不能被打断，自动路径就等待
——它不会去武装那个覆盖动作，那是只有人才能做的判断。一台看上去卡住的设备其实
在告诉你原因：`GET /api/v1/update` 带有一个 `deferred` 条目，点名上一次自动尝
试没有推进的理由，以及它已经等了多久。

**失败过的版本不会被再装一次。**如果一个新槽发生了回滚，设备会记下那个版本，
自动路径在操作员清除这条记录之前都拒绝它。你仍然可以手动安装它：这条拒绝约束
的是自动化，不是你。

> status: shipped — evidence: `pkgs/mosd/mosd/src/update_auto.rs`, `docs/design/updates.md`

`auto` 已经实现，但**没有任何自动化测试**，也没有在真实硬件上跑过台架。对于一
台你够不着的设备，请把它当作未经验证的功能。

### 设置存在哪里，以及复位对它们做什么

更新设置是设备数据分区上的一个 JSON 文档，`/mos/config/updates.json`，每次决策
都重新读取——源 URL 与渠道、上面那个模式、字节预算、online/metered/offline 网络
模式、检查间隔、只对安装生效的维护窗口，以及重启门禁的上限。每一个值都有一个
**烤进镜像的内置默认值**，文档只覆盖它点名的那些。它**失败即关闭**：存在但解析
不了的文档会拒绝它本可以限制的每一个动作，而不是变成"不受限"然后在计费链路上拉
一个 bundle。被拒绝时，答复会点名是哪条规则拒绝的。

`GET /api/v1/provisioning/status` 会分别报告内置值、你的覆盖值和生效值，这就是
*这台设备为什么在那个渠道上*的答案。

**配置复位或出厂复位会把这一切都还原成内置默认值**——包括更新服务器地址。那既是
一条恢复路线，也是——当镜像本身没有指定服务器时——一种让设备从此没有更新服务器的
方式；[recovery.md](recovery.md) 第 3 步是完整的警告，以及事先怎么确认自己属于
哪一种情况。

内置 UI 的"系统"页面上带有同样的检查、下载与安装动作。

**更换更新服务器，以及服务器搬走了怎么办。**地址由你来设；设备愿意**接受**什么
则不是。经过认证的操作员可以把设备重新指向另一台服务器，而没有任何设置、文件或
API 调用能让设备去信任另一把签名密钥——那要靠一次镜像。所以当一台服务器消失时，
回来的路有三条，按顺序：

1. **把设备重新指向**新地址。不需要镜像，也不需要物理接触。
2. **离线导入**，从可移动介质（见下）。完全不需要服务器。
3. **整盘重刷。**它同时会更换设备身份，所以排在最后
   （[recovery.md](recovery.md) 第 7 步）。

剩下没有答案的情形很窄，值得点名：一台**谁也认证不上去**的设备——没有可用凭据、
也没有物理接触——如果它的服务器又消失了，就完全够不着了。这里刻意没有一条能修好
它的远程通道。

> status: shipped — evidence: `docs/design/updates.md`, `pkgs/mosd/apid/openapi.json`

对计费或完全离线的站点，离线路线是同样的验证换一种传输：`rauc-update import`
从可移动介质读取 lockbox，用同样的烤入锚走完验证，把 bundle 暂存进同一个工作
区；随后的安装就是对那个路径的一次普通安装。没有任何开关能跳过其中任一步，
介质上那个 bundle 本身也不是可安装路径。

> status: shipped — evidence: `docs/design/updates.md`, `pkgs/rauc-sign/`

## 3. 回滚

- **自动。**启动失败、或启动了但没过健康门的槽，其额度永远不会被补满；
  接下来的复位会把额度耗尽，引导加载程序回到之前的槽。当两个槽都耗尽时，
  cx3576 的引导加载程序补满所有计数器并复位——设备持续循环而不是变砖，
  出路是恢复路径（[recovery.md](recovery.md)）。
- **有防护的手动回滚。**`POST /api/v1/update/rollback` 针对自动路径永远抓不到
  的情形：一个能启动、但表现异常的槽。它不接受请求体——目标不是调用方能指定
  的——并且只做一件事：把**已启动**的槽标记为 bad，从而让引导加载程序去挑另一
  个。它从不标记目标槽，因此在结构上无法确认一个从没被任何一次启动验证过的
  槽；它也不重启：真正兑现回滚的是第二次显式重启，走同一个可安全重启门禁。
- **回滚只能向后走，无法确立这一点时就拒绝。**目标必须是两次安装中严格**更旧**
  的那一个。拒绝理由是点名的，所以"不行"会说明是哪一种：没有可解析的另一个
  槽；另一个槽就是已启动的槽；另一个槽从未被安装过；引导加载程序已经把另一个
  槽判定为 bad；另一个槽比正在运行的系统**更新**，那是待装或被跳过的更新而不
  是回滚目标；两个安装时间戳无法排序；或者已启动的槽自己还处于待确认状态，此
  时手动回滚会与正在扣除的启动额度相撞。排序类的两种情形刻意**失败即关闭**——
  时间戳相同正是一次同时写入两个槽的出厂刷写的形状，而那种情况下另一个槽从未
  运行过。
- **原始标记**仍然留在旁边，用于健康门无法裁决的情形——例如操作员已判定可以
  接受的失败单元：`POST /api/v1/update/mark`，对已启动槽或另一槽标记
  `good`/`bad`。激活（`active`）和具体槽名在两个接口上都被拒绝；激活是安装器
  的职责。

内置 UI 的"系统"页面带有回滚动作，并显示防护的裁决与理由。

一个值得知道的代价：只有较新发布版才认识的设置 schema 键，在较旧发布版
启动时会被丢弃——设置存储通过剥掉不认识的部分来容忍较新的文档。宁可及时
确认或及时回滚，也不要让旧槽长时间运行在新 schema 的设置上。

**未在硬件上验证：**引导加载程序随后是否真的回落，是没有任何板卡产出过的
台架证据。防护逻辑、它的各种拒绝以及额度算术都是在硬件之外测试的。

> status: shipped — evidence: `docs/design/uboot-ab-handshake.md`, `pkgs/mosd/mosd/src/rauc.rs`

## 4. 更新信任链是什么、不是什么

一个发布版由两个互不相关的体系签名两次：RAUC bundle 携带 CMS 签名，在
设备上对照 `/etc/rauc/keyring.pem` 验证；TUF 仓库元数据在四个角色密钥
（root 离线）下固定 bundle 的摘要、长度和 verity 根哈希。验证这份元数据的
设备侧验证器如今随更新客户端一起装在镜像里。仪式与保管规则是签名 runbook，
[../design/release-signing.md](../design/release-signing.md)。

**每一把锚从哪里来。**两者都随镜像走。RAUC 密钥环在构建时被放进只读根；受
信任的软件包签名密钥以内联形式烤进同一个镜像，客户端只从那里读，别处一概不
读——没有要预置的文件，没有开关，也没有任何设置能让操作员或某个车队指定另一
把密钥。这正是更新**地址**属于一个普通设置、而更新**信任**不是的原因。

已点名的缺口：还没有任何镜像随附生产密钥环（未提供材料的构建会生成一个高调
标记的开发级信任根），已部署设备上也没有密钥环轮换渠道，所以一把被攻破的签名
CA 仍然只能靠整盘重刷。没有拿到软件包签名密钥的构建会烤进一个空列表并声明这
一点——这样的镜像根本无法验证任何更新包。见 [security.md](security.md)。

> status: shipped — evidence: `docs/design/release-signing.md`, `pkgs/rauc-sign/`

## 5. 还欠着的部分

- **一次被确认的启动，还没有被作为"已确认"报告出来。**生命周期从启动健康门
  尚未写入的一条记录去推导 "validating" 与 "succeeded"，因此一台健康收敛的
  设备读出来是朴素的 `idle`——是诚实的沉默，而不是猜出来的成功。此时请用槽
  列表和已启动槽来确认更新。推导本身已经实现并有测试。
- **这一切都没在硬件上跑过。**下载或安装中途断电、启动额度耗尽、一次真实的
  自动回落、在不匹配的板卡上被 RAUC 拒绝的不兼容 bundle、把真实介质上的 DATA
  写满——每一项都有硬件之外的逻辑测试，背后没有任何台架运行。设计记录的故障
  表逐条写明每种故障究竟在哪里被证明。
- **`auto` 没有测试。**自动路径已经实现，却没有一行被测试执行过，也没有在
  板卡上跑过。它是第一个会在无人看管时重启设备的能力，所以这是本列表里分量
  最重的一条。
- **STATE 上的元数据目录**属于没有任何镜像执行的预置工作：客户端的默认值把
  `/var/lib/mos/update/` 指为元数据镜像与回滚状态的位置，而没有东西创建它。
  信任锚已经不在这份清单上了——它是烤进去的（第 4 节）。
- **没有任何 API 能改更新设置。**它们是设备上的一个文档；读它有路由，写它还
  没有，所以今天要设 `auto` 或一个维护窗口，只能在设备上编辑那个文件。

> status: unsupported
